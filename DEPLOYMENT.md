# Private Clip Clap analytics

The public release remains **v0.11.0**. Do not replace `latest.json` with the local v0.11.1 candidate until production analytics and privacy checks are complete.

## Activate the backend

1. Use one Supabase project. Run `supabase/001_analytics.sql` once in its SQL editor. No tables or RPCs are readable or executable by `anon` or `authenticated`. The service-role key is used exclusively by Vercel server functions.
2. In Supabase Authentication, create the single owner user with the owner's email and confirm that address. Copy its user UUID. Disable public signups. In the **Magic Link email template**, include `{{ .Token }}` so email sign-in sends a numeric OTP. Set OTP expiration to 10 minutes. Configure a production SMTP provider and test delivery; Supabase's default sender is restricted and is not a production email service.
3. In the existing Vercel project's Production environment, set `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `OWNER_EMAIL`, `OWNER_USER_ID`, `RATE_LIMIT_SECRET`, `CRON_SECRET`, and `SITE_ORIGIN=https://clipclap.mskmpt.pro`. Generate each of the two secrets independently using at least 32 random bytes. No value should use a `VITE_`, `NEXT_PUBLIC_`, or other public prefix. Do not commit `.env` files. GitHub public releases work without a token; optional `GITHUB_TOKEN` needs only public repository read access.
4. Deploy this repository using **Other** framework, repository root, `npm run build`, output `public`, and Node 22.x. `vercel.json` provides these build/output settings, `/admin` and `/privacy`, response protection and a daily maintenance cron. Remove any conflicting old project-level output override. Redeploy after setting environment variables.
5. Open **https://clipclap.mskmpt.pro/admin**. Request an owner code, sign in, refresh, and sign out. Confirm another account and an unauthenticated `/api/dashboard` request cannot read metrics. Confirm the same-owner UUID and confirmed email checks pass against real Supabase Auth.
6. In Vercel's cron settings, run `/api/maintenance` once to establish the GitHub baseline and confirm the daily job succeeds. The automatically supplied `Authorization: Bearer CRON_SECRET` is required. Investigate failed jobs so retention remains enforced. Do not enable request-body/header logging, third-party APM body capture, or log drains containing credentials/content. Review the hosting providers' operational log retention separately; network services necessarily process IP addresses even though analytics never persists raw IP.
7. Verify all three public download links still point to v0.11.0 and that `latest.json` matches the release installer. Enable analytics in the locally installed v0.11.1 candidate, create a clip and export it, then verify the private counts. Turn analytics off and verify no new outbound events. Only after these production checks may the candidate be considered for a public app release.

All collection and dashboard routes fail closed with a generic 503 while backend environment variables are absent. The homepage and installer navigation continue working. No cloud credentials or database project are included in this repository.

## Measurement definitions

- App analytics is opt-in and off by default. `first_install` means the first successful **consenting observation**, including users upgrading from versions that did not include telemetry. It is not a count of all downloads or all historical installations. The locally random UUID survives normal updates and standard uninstall/reinstall when saved app data remains.
- `first_install` uses a stable event ID. SQL also checks the installation row, preventing duplicate installs even if a different event ID is retried. Other events have UUID event IDs. The local queue holds at most 100 events for 7 days. Failed sends retry after 30 seconds; turning analytics off clears the queue. Graceful close queues `app_close` for best-effort delivery, including the next launch.
- Active Today: distinct installations with `app_open` in the current UTC day. Active 7/30 Days: distinct installations whose latest `app_open` is within the rolling period. Daily charts use UTC event dates. Limited delayed app delivery retains its original event time; first consenting observation uses server time.
- Latest version is read from the unchanged canonical site `latest.json`. Distribution and latest-version users use the latest `version_seen` per installation. Delayed events cannot overwrite a newer observation. No installation IDs leave the authenticated aggregation endpoint.
- Website estimated unique visitors are **daily browser sessions**, stored in sessionStorage and rotated each UTC day. Summing these estimates over a date range does not identify unique people across days. No referrer, query string, IP, browser attributes, or hardware fingerprint is collected. DNT and GPC opt out. Download clicks include only a fixed page, placement and the validated manifest version, when available.
- GitHub counts are cumulative installer asset downloads, cached for 15 minutes in warm functions. The first per-version snapshot is a baseline. Daily deltas are observed increases between snapshots; gaps are attributed to the next observation and cannot reconstruct true download dates. No historic daily values are invented.
- Date filters affect website visits, clicks, selected-range new installs and daily charts. Lifetime totals, rolling active-user cards and current version distribution remain explicitly labeled as such.

## Retention

Daily cron calls `analytics_cleanup`: app/website event rows 90 days; visitor IDs 31 days; per-install daily activity keys 35 days; version-per-day IDs 395 days; installation summaries 395 days after last event. Rate-limit HMACs expire after 2 minutes and are removed on the next request or daily cleanup. The HMAC key changes by minute and scope and is never joined to analytics rows. Daily aggregate totals and GitHub snapshots contain no user identifiers and can remain for historical reporting. Once an installation summary expires, returning installs can contribute new activity/version observations; historical aggregate totals remain. An unusually late replay of `first_install` after the installation summary expires cannot be deduplicated forever; public anonymous counts are estimates, not billing or license enforcement.

## Local checks

`npm ci` then `npm test` runs PostgreSQL-compatible PGlite migration/aggregation/RLS/retention tests plus strict schema/privacy/browser tracking tests. `npm run build` copies only an explicit list of static UI assets into `public`; server files, migrations, environment examples and tests are excluded from static hosting. `api/` is bundled as Vercel functions.

The repository's `tests/browser-qa.mjs` additionally exercises a real Edge browser and real SQL migration against the local app workspace. It requires the Clip Clap application source two directories above this site checkout, its Python runtime, and a Playwright module path argument. Its email provider is simulated with synthetic test credentials; GitHub counts and application export are real. It is test infrastructure only and has no production bypass.
